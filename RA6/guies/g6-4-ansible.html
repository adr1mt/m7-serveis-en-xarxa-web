Què hi ha en aquesta guia

Documentació oficial: docs.ansible.com/ansible/latest.

  • Punt de partida: una màquina de control amb Ansible instal·lat i accés per clau SSH a les màquines que administrarà. L'accés per clau es munta amb G6.1: no es repeteix aquí.
  • Les màquines administrades no necessiten cap paquet d'Ansible: només SSH i Python.

Instal·lar Ansible a la màquina de control

  1. Instal·la el paquet i comprova la versió:

    Terminal
    sudo apt update
sudo apt install -y ansible
ansible --version

L'inventari i la primera prova

  1. Crea el fitxer hosts amb un grup i l'usuari amb què Ansible es connecta per SSH:

    Fitxer · Ansible
    [servidors]
192.168.1.10

[servidors:vars]
ansible_user=usuari

    Substitueix 192.168.1.10 per la IP del node i usuari pel compte que hi té accés per clau.

  2. Comprova que hi arriba amb el mòdul ping, que no fa cap ping ICMP: comprova que Ansible pot connectar i executar-hi Python:

    Terminal
    ansible -i hosts servidors -m ping

    Resposta esperada: SUCCESS per a cada màquina del grup.

Anatomia d'un playbook

Al recap, ok inclou totes les tasques reeixides, també les que han modificat l’estat. changed n’és el subconjunt amb canvis. La prova d’una segona execució sense modificacions és changed=0, no ok=0; cal comprovar també failed=0 i unreachable=0.

Un playbook és un fitxer YAML amb una llista de plays. Cada play indica hosts (a quin grup de l'inventari s'aplica), become (si cal elevar privilegis) i una llista de tasks. Cada tasca té un nom descriptiu, un mòdul i els seus paràmetres.

Fitxer · Ansible
- hosts: servidors
  become: true
  tasks:
    - name: instal·la el paquet curl
      apt:
        name: curl
        state: present

YAML es sagna amb espais, mai tabuladors, i el nivell de sagnat és el que marca a quin bloc pertany cada línia: un espai de més o de menys trenca el playbook o li canvia el significat sense avisar.

Mòduls habituals

MòdulParàmetre clau
aptname, state: instal·la o esborra paquets.
copysrc / dest: copia un fitxer tal qual.
templatesrc / dest: com copy, però processant Jinja2.
servicename, state: arrenca, atura o reinicia un servei.
username, groups: crea o modifica un usuari.
hostnamename: fixa el nom de la màquina.
lineinfilepath, line: afegeix o assegura una línia dins d'un fitxer.
filepath, state: crea directoris o fixa permisos.

Variables per grup

Un fitxer group_vars/<grup>.yml es carrega sol quan el seu nom coincideix amb el d'un grup de l'inventari: group_vars/servidors.yml per al grup [servidors]. No cal importar-lo enlloc del playbook.

Crea la carpeta i el fitxer de variables:

Terminal
mkdir -p group_vars
nano group_vars/servidors.yml
Fitxer · Ansible
paquet_web: apache2

Dins d'una tasca la variable es fa servir entre claus dobles:

Fitxer · Ansible
- name: instal·la el servidor web
  apt:
    name: "{{ paquet_web }}"
    state: present

Plantilles Jinja2

Un fitxer a templates/*.j2 és com qualsevol fitxer de configuració, però amb variables entre {{ }}. El mòdul template el processa i en desa el resultat a la màquina administrada. A més de les variables pròpies, Ansible ja coneix dades de cada màquina dins de ansible_facts, com ansible_facts['default_ipv4']['address'] (la seva IP) o ansible_facts['hostname'] (el seu nom).

Crea la plantilla que es convertirà en la pàgina inicial del node:

Terminal
mkdir -p templates
nano templates/index.html.j2
Plantilla HTML · Jinja2
<h1>Servidor: {{ ansible_facts['hostname'] }}</h1>
<p>Adreça: {{ ansible_facts['default_ipv4']['address'] }}</p>

Crear el playbook i el handler

  1. Crea site.yml amb el play complet:

    Fitxer · Ansible
    - hosts: servidors
  become: true
  tasks:
    - name: instal·la el servidor web
      apt:
        name: "{{ paquet_web }}"
        state: present

    - name: genera la pàgina d'inici
      template:
        src: templates/index.html.j2
        dest: /var/www/html/index.html
      notify: reinicia apache

  handlers:
    - name: reinicia apache
      service:
        name: apache2
        state: restarted

    El handler només s'executa si la tasca que el notifica acaba en changed, i sempre al final del play, encara que l'hagin notificat diverses tasques.

Executar el playbook

  1. Comprova la sintaxi i executa'l:

    Terminal
    ansible-playbook -i hosts site.yml --syntax-check
ansible-playbook -i hosts site.yml

    Si l'usuari no té sudo sense contrasenya, cal afegir --ask-become-pass perquè la demani.

  2. Llegeix el resum final: ok compta tasques reeixides, incloses les modificades; changed compta el subconjunt que ha canviat l’estat. failed indica errors i unreachable manca d’accés al node.

  3. Torna'l a executar. Si el playbook és idempotent, la segona vegada tot surt ok i cap tasca surt changed.

  4. Simula sense aplicar amb --check: diu què canviaria sense tocar res.

    Terminal
    ansible-playbook -i hosts site.yml --check

Comprovar-ho de conjunt

  1. Executa el playbook dues vegades seguides.

  2. A la segona, el resum final no mostra cap tasca changed: tot ha quedat ok.

Bones pràctiques

  • Mai root per SSH: connexió amb un usuari normal i become: true només on cal elevar privilegis.
  • Una tasca per cosa, no una tasca per paquet: un sol apt amb una llista de paquets, en lloc de repetir la tasca.
  • Tot idempotent: executar el playbook dues vegades ha de donar el mateix resultat que una.
  • Els handlers, només per a canvis que de debò requereixen reiniciar algun servei.

Problemes

El playbook falla amb un error de sintaxi imprecís

Causa Sagnat incorrecte al YAML: un espai de més o de menys, o un tabulador colat.

Solució Revisa el nivell de sagnat de la línia que assenyala l'error; YAML és sensible a espais, no a tabuladors.

Ansible demana contrasenya de SSH a cada execució

Causa No hi ha clau pública copiada a la màquina administrada.

Solució Munta l'accés per clau amb G6.1 abans de continuar.

Una tasca falla per permisos, tot i que l'usuari sembla correcte

Causa Falta become: true al play o a la tasca, i s'intenta amb un usuari sense privilegis.

Solució Afegeix become: true on calgui elevar privilegis.

El handler no s'executa

Causa La tasca que l'hauria de notificar no ha produït cap canvi (ok, no changed).

Solució És el comportament esperat: si no hi ha canvi, no cal reiniciar res.

Les variables de group_vars no s'apliquen

Causa El nom del fitxer no coincideix exactament amb el del grup de l'inventari.

Solució Renombra'l perquè coincideixi (group_vars/servidors.yml per al grup [servidors]).
