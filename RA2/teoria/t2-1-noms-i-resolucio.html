Noms i resolució al client

Què passa dins del teu equip entre que escrius un nom i surt una adreça IP.

Què sabràs fer en acabar

  • Explicar per què les xarxes treballen amb noms i no amb adreces.
  • Distingir els dos mecanismes de resolució: fitxer local i DNS.
  • Saber en quin ordre consulta el teu equip cada mecanisme.
  • Fer servir resolvectl, host i dig.
  • Entendre què és la memòria cau i per què de vegades enganya.

El problema que resol el DNS

Al RA1 vas repartir adreces amb DHCP. Però ningú escriu 142.250.185.3 al navegador: escrivim noms. Algú ha de convertir el nom en adreça abans que la màquina pugui enviar cap paquet.

Els noms tenen dos avantatges que les adreces no tenen:

  • Es recorden. moodle.elpuig.xeill.net contra una IP qualsevol.
  • Sobreviuen als canvis: si el servidor canvia d'adreça, el nom continua sent el mateix.

Aquesta conversió es diu resolució de noms, i el sistema que la fa a Internet és el DNS (Domain Name System).

Dos mecanismes, i un ordre

El teu equip pot resoldre un nom de dues maneres: mirant un fitxer local o preguntant a un servidor. No en tria una a l'atzar: hi ha un ordre escrit.

MecanismeOn miraLímit
Fitxer local/etc/hostsNomés el que hi has escrit tu
mDNSPregunta a crits a la xarxa localNomés noms acabats en .local
DNSUn servidor de nomsCal tenir-ne un configurat

L'ordre el marca el fitxer /etc/nsswitch.conf, a la línia hosts:. Primer el fitxer local, després la resta. Per això una línia a /etc/hosts guanya sempre al DNS.

Qui pregunta de veritat: systemd-resolved

A Ubuntu, les aplicacions no parlen amb el servidor DNS directament. Parlen amb un servei local, systemd-resolved, que escolta a l'adreça 127.0.0.53 i fa de intermediari.

Serveix per a dues coses:

  • Memòria cau: si algú ja ha preguntat aquell nom fa poc, respon a l'instant.
  • Un sol punt: si canvia el servidor DNS, les aplicacions no se n'assabenten.

És un stub: no sap resoldre pel seu compte, només reenvia al servidor DNS que li han dit. I aquest servidor, en una xarxa normal, l'hi ha donat el DHCP.

El fitxer /etc/resolv.conf ja no és el que era

Durant anys, el servidor DNS s'escrivia a mà a /etc/resolv.conf. Avui aquest fitxer el genera systemd-resolved i conté sempre el mateix: 

# This file is managed by man:systemd-resolved(8).
nameserver 127.0.0.53
options edns0 trust-ad
search .

Aquesta adreça no és el teu servidor DNS: és el servei local. Per veure el servidor de veritat cal preguntar-l'hi: 

resolvectl dns
Link 2 (enp1s0): 10.0.0.1

Editar /etc/resolv.conf a mà no serveix de res: es torna a generar.

El domini .local no és teu

És molt habitual batejar la xarxa de casa o de l'aula com empresa.local. És una mala idea: el sufix .local està reservat per a mDNS, el mecanisme que fa que les impressores es trobin soles.

Conseqüència pràctica: quan preguntes per un nom acabat en .local, el sistema el pot enviar per mDNS i no arribar mai al teu servidor DNS. El símptoma és típic: el client rep bé la IP i el DNS, però no resol els teus noms.

Per als dominis interns fes servir .internal, reservat oficialment per a ús privat des del 2024, o un subdomini d'un domini teu.

Mirar com resol la teva màquina

Amb qualsevol Ubuntu connectat a la xarxa del centre:

  1. Mira quin servidor fa servir i quin domini de cerca té:

    resolvectl status

    Fixa't en Current DNS Server i en DNS Domain.

  2. Resol un nom i mira d'on surt la resposta:

    resolvectl query www.upc.edu

    L'última línia diu Data from: network la primera vegada i Data from: cache la segona, molt més ràpida.

  3. Consulta un servidor concret, saltant-te el servei local:

    host www.upc.edu 9.9.9.9
dig @9.9.9.9 www.upc.edu +short

  4. Demana un tipus de registre diferent de l'adreça:

    dig upc.edu MX +short      # servidors de correu
dig upc.edu NS +short      # servidors de noms

  5. Fes trampa amb /etc/hosts per comprovar l'ordre de resolució:

    echo "127.0.0.1 provaordre.test" | sudo tee -a /etc/hosts
getent hosts provaordre.test

    Esborra la línia quan ho hagis vist.

Ubuntu 26.04 dig i host ja vénen instal·lats. Si et falten: sudo apt install bind9-dnsutils.

Criteris professionals

  • /etc/hosts és per a proves, no per a administrar una xarxa. No escala i ningú se'n recorda.
  • No editis /etc/resolv.conf: el DNS es configura al Netplan o s'obté per DHCP.
  • Comprova amb dig @servidor quan sospitis de la memòria cau: així preguntes directament.
  • Fes servir .internal per als dominis interns, mai .local.
  • Dos servidors DNS als clients, sempre que puguis: si en cau un, la xarxa continua.

Errors habituals

ping 9.9.9.9 va, però ping www.upc.edu no

Causa La xarxa funciona; el que falla és la resolució de noms.

Solució resolvectl status: mira si hi ha cap servidor DNS configurat i si respon amb dig @aquellaIP.

Has canviat una adreça i el nom encara apunta a l'antiga

Causa Memòria cau. El teu equip guarda la resposta el temps que digui el TTL.

Solució sudo resolvectl flush-caches, i comprova després amb dig contra el servidor.

Un nom es resol a la teva màquina i a la del costat no

Causa Te'l resol una línia de /etc/hosts que només tens tu.

Solució getent hosts nom i revisa el fitxer. Si hi és, treu-la i posa el registre al servidor DNS.

Resum

  • Resoldre un nom és convertir-lo en adreça IP abans d'enviar res.
  • L'ordre el marca /etc/nsswitch.conf: /etc/hosts guanya al DNS.
  • A Ubuntu qui pregunta és systemd-resolved, al 127.0.0.53, amb memòria cau.
  • /etc/resolv.conf és generat: no s'edita.
  • .local està reservat per a mDNS; per a xarxes internes, .internal.
